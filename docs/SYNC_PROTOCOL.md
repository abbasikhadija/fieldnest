# Synchronization protocol

M0 contains no synchronization engine, queue, persistence or backend. This document establishes constraints for the detailed M3 design; it is not an implemented API contract.

Each queued operation will have a stable UUID, authorized record identifier, expected base version, validated payload and account scope. The operation identifier remains unchanged across retries, including timeouts and lost acknowledgments. Local record and queue edits must commit atomically through Dexie before announcing a save.

A PostgreSQL transactional function must authenticate and authorize every operation, validate its structure, deduplicate by authorized operation identity, check the expected version and atomically commit both the record and stored result. Retrying a committed operation returns its stored acknowledgment. Define identifier-reuse/payload mismatch rejection and retention before implementation.

Client acknowledgment processing must atomically persist accepted version/result and finalize its queue entry. A lost response leaves the entry retryable. Dependent operations preserve order per record; unrelated failures are isolated. Retry uses bounded exponential backoff with jitter. Active-app events trigger processing; browser-closed synchronization is not promised.

A version mismatch preserves local and remote snapshots. Manual resolution displays differences and creates a new operation against the reviewed server version. Repeated conflicts require review again, never unconditional overwrite. Account changes cannot expose another user's records or silently delete pending work. Multi-tab coordination is an optimization; server idempotency remains mandatory.

Before M3 finalize operation schema, RPC/error contract, dependency ordering, queue leasing, retention and security rules. Verify against real database transactions, including duplicate delivery, lost acknowledgment, interrupted local acknowledgment and two-device conflicts. No guarantees above have been tested in M0.

## M1 boundary
Local demo inspection saving is now implemented with Dexie; the protocol above remains design intent for future connected mode. The local revision is a device-only concurrency token, not a server version. No operation identifiers, mutation queue, remote processing, acknowledgments or synchronization workers exist yet. Demo records never display server acceptance or pending-sync indicators. Detailed local save/recovery semantics are documented in ARCHITECTURE.md.

## M2 boundary
Server inspection and assignment tables, constrained shared inspection_records and RLS now exist. The version column is reserved for the future version-checked protocol; M2 clients can only read. No processed-operation table, idempotency function, outbox, retry worker, record upload or conflict-resolution endpoint is implemented. Connected data is not stored in the demo database or automatically synchronized. M3 must define and test the complete mutation/acknowledgment contract before enabling any connected edits.

## M3 implemented wire contract (designed before implementation)
Account-scoped Dexie databases hold downloaded assignment context, the latest local record, local revision, server version, and an immutable outbox snapshot. A record has at most one in-flight operation; subsequent edits update the record and remain dirty until the previous acknowledgment advances its base version. Operations are UUIDs generated inside a local save transaction; retries never change their payload or ID. Device saves and queue creation are atomic. Acknowledgment transactions update the server snapshot/version, remove the exact operation, and enqueue newer local content against the acknowledged version. No successful sync label precedes that transaction.

`apply_inspection_operation(operation_id uuid, inspection_id uuid, base_version integer, payload jsonb)` authenticates and checks current assignment on every call, including replay. Payload contains exactly answers, notes, status. A per-record row lock serializes writers; an account/operation advisory lock serializes duplicate deliveries. A private receipt table stores request and result indefinitely (no automatic pruning in M3). Identical replay returns the original accepted/conflict result; reuse with different input fails. Accepted mutations and receipts commit together. Conflict results contain the current server snapshot and stop that record while preserving the local snapshot. Manual comparison/resolution belongs to M4. Completed records cannot be edited; stale completion produces a conflict.

Workers claim operations with a transactional 45-second lease, send at most 10 per pass, and use 20-second request deadlines. Failure persists bounded exponential backoff (1s–60s plus up to 25% jitter); permanent validation/authorization failures stop that operation visibly. Startup, online, visibility and explicit Sync trigger processing; a timer handles due retries while active. Other records continue after a failure. Leases are coordination, not correctness: duplicate requests remain safe server-side. Closing a tab leaves the durable operation retryable after lease expiry.

Cached work can be opened offline only for the identity in the existing project-scoped Auth session, never an arbitrary account selector. This is a local convenience, not live authorization verification; server operations always reverify. Sign-out hides the workspace before awaiting Auth, retains unsynchronized data, and never clears a database. Reopening online refreshes clean records only; dirty/queued/conflicting content cannot be overwritten by downloads. Revoked access blocks uploads and retains recoverable local work. Shared-device/browser storage limitations remain explicit.

## M3 request and receipt validation follow-up
Protected downloads and uploads capture the active session, verify that exact access token belongs to the expected account, and explicitly bind the resulting HTTP request to the verified token. A later change to the shared Supabase client's active session cannot silently substitute another account's JWT. Expired/changed identities send no protected request; timed-out uploads also check the aborted signal after identity verification.

An accepted receipt must match the durable queued inspection, base version + 1, answers, notes and lifecycle status. Answer comparison ignores JSON key ordering but rejects missing/extra or changed answers. Conflict receipts cannot move the server version behind the queued base version. Validation failure leaves the outbox and local record unchanged. Finalization uses the stored operation revision and identity, not a mutable worker object, so a mistaken caller snapshot cannot manufacture a newer edit or remove another inspection's operation.

## M4 resolution contract (defined before implementation)
Conflicts remain stopped until explicit review. The UI compares every checklist answer, notes and lifecycle status in the saved device copy and a version-labelled server snapshot, highlights differences with text, and can refresh the server snapshot without changing device edits. No automatic merge occurs. Offline review uses a clearly labelled last-known server snapshot; any upload still checks that version.

Connected Dexie schema v2 adds resolutions, an account-scoped local recovery history. Resolving requires the exact local revision and reviewed server version. A single transaction archives both snapshots and the blocked original operation, replaces/removes that operation, advances the local revision and either adopts the reviewed server copy or queues a fresh immutable UUID against its server version. Invalid, duplicate, stale-tab or failed storage decisions leave recoverable work unchanged. A newer server update after review produces another ordinary version-checked conflict; users must review again. Completed server records cannot be overwritten, so only adoption/download is offered. No new server RPC or mutation grants are needed; M3's authorization, immutable receipt and version checks remain authoritative.
